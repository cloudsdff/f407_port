# AI 协作会话纪要

> 时间：2026-11-16 ~ 2026-11-21
> 形式：AI 助手（DeepSeek）负责代码实现、寄存器级排障、文档起草；
> 人负责硬件接线、上电验证、现象观察与最终决策。

## 一、协作方式

| 角色 | 做的事 |
|---|---|
| **AI** | 写代码、算时钟/波特率、读寄存器定位故障、起草文档、给出验证脚本 |
| **人** | 接线、上电、拔插故障注入、按脚本操作、判定现象是否符合预期 |

**关键约束**：AI 看不到板子。所有结论都要靠"人观察到的现象"或"AI 通过 J-Link 读到的寄存器"来确认。
所以每个功能都以"能在串口上看到某一行为通过标准"。

## 二、按阶段的产出

### 阶段 1：环境与最小工程（11/16–11/17）

- 问题：手上只有 F103C8T6，HAL 库、工具链、烧录器都不齐
- AI 做的：列出工具链清单（gcc 14.3 / CMake / Ninja / CubeMX 6.18）、
  给出 `cmake --preset Debug` 的坑（相对路径的 toolchain file 会被静默忽略）、
  给出 J-Link Commander 的烧录脚本
- 人工验证：串口打印 `SYSCLK=72000000 HCLK=72000000 PCLK1=36000000 PCLK2=72000000`

### 阶段 2：FreeRTOS + TIM4 时基（11/17）

- 问题：F103C8 没有 TIM6/TIM7，HAL 时基没法定
- AI 做的：改用 **TIM4** 做 HAL 时基，SysTick 让给 FreeRTOS
- 人工验证：两个任务分别 200 ms / 500 ms 稳定运行，实测 log 周期 503 ms

### 阶段 3：三层骨架（11/18）

- AI 做的：设计 `Err` 错误码（10 种）、`Uart` 纯虚接口、`log` 接口，
  给出 `-fno-exceptions -fno-rtti` 的 C++17 配置
- 人工验证：`app/app_main.cpp` 编译通过且能调用 `bsp::uart1`，业务层零 `HAL_`

### 阶段 4：UART 阻塞 + DMA（11/19）★ 排障量最大的一段

三个坑，全部由 AI 读寄存器/日志定位、人操作验证：

| 坑 | 现象 | 定位过程 | 结论 |
|---|---|---|---|
| 没配 DMA | 整机停住、一个字都不输出 | AI 建议先加 `hdmatx == nullptr` 守卫 | HAL 解引用空指针 → 改为返回 `Err::NotInit` |
| 只开 DMA 中断、没开 USART1 全局中断 | 发完第一帧后永久安静 | AI 让读 `CAN_MSR` 式的思路，改读 `it.c` 有无 `USART1_IRQHandler` | HAL 的 DMA 发送是两段式中断，缺 TC 那半 → `gState` 卡在 BUSY_TX，**所有 printf 被丢弃** |
| DMA 发送中调 printf | 日志缺字、整行消失 | AI 让把测试改成"发完再打" | printf 和 DMA 抢同一个串口 |

最终实测：100 帧 × 256 字节 = 25600 字节，PC 端逐字节校验 **102 帧零错位**，带宽利用率 96.5%。

### 阶段 5：I2C + MPU6050（11/19）

- AI 做的：`bsp::I2c` 接口（含 `probe` / `recover_bus`）、`module::Mpu6050`（四道初始化关卡）
- 发现的真实问题：静止加速度模长 **1.119 g**（理想 1.000 g）→ 零偏 + 标度误差，
  这正是任务02"上电自校准"的动机
- 人工验证：拔 SDA → 4 ms 内恢复 → 插回数据自动回来

### 阶段 6：CAN 双节点（11/20）★ 卡了最久的一段

| 现象 | AI 判断 | 实际原因 |
|---|---|---|
| `can: start failed`（第一次） | 以为要接收发器才有电平 | 正确：CAN 控制器退出初始化需要 11 个隐性位 |
| `can: start failed`（第二次） | 以为是 B 板拉死总线 | **模块没 5V**：蓝药丸靠 J-Link 3.3V 供电时 5V 引脚没电 |
| 单节点 `err=0` 却能发 | 以为是模块自环 | 其实是 B 板在正常 ACK |
| `rx≈tx` 以为是自环 | 判断错了 | 用 ID 过滤一验就知道是对方发的 |

**排障链**（这条最有价值）：
```
can: start failed → CAN_MSR=0x409(INAK=1) → CAN_ESR=0(没发出去过)
→ GPIOA->IDR bit11=0(PA11 被拉低) → 模块 VCC 无 5V
```

最终：F103 ↔ F103 互通 1800+ 帧；之后 F103 ↔ **F407** 跨型号互通。

### 阶段 7：任务划分 + 异步日志（11/20）

- AI 做的：把同步日志改成"队列 + 低优先级任务"
- 踩的坑：
  - 日志函数在栈上开两块 96 字节缓冲 → `Comm` 任务 512 B 栈直接溢出 →
    表现为 `CFSR=0x400 IMPRECISERR`（不精确总线错误），**崩的地方和出错的地方无关**
  - 日志队列深度 8 不够 → `logdrop=29`
- 修复：单缓冲、栈加到 1024、堆 8192→10240、队列 12×80、Log 任务优先级提到 `BelowNormal1`
- 最终：`logdrop=0`，`stack free: Comm=352 Sensor=360`

### 阶段 8：六条失败路径（11/21）

AI 写测试开关（`LOG_OVERFLOW_TEST` / `STACK_TEST_SMALL`）+ FreeRTOS 栈溢出钩子。

**钩子第一版是错的**：调用了带队列的日志函数，而钩子运行在中断关闭上下文，
队列不可用 → 钩子自己发不出消息，系统依旧静默停住。
改成直接写 USART 后成功报出 `!!! STACK OVERFLOW in task [Comm] !!!`。

> 教训：**"报错路径"本身也必须被测试。**

### 阶段 9：F407 移植（11/21）

- 编译**一次通过**（业务层零改动）
- 三个真实差异：
  1. 句柄名 `hcan` → `hcan1`
  2. **CAN 位时序必须重算**：PCLK1 从 36 → 42 MHz，`4/15/2` 改成 `6/11/2`
  3. **F4 把 CAN 错误中断拆成独立向量** `CAN1_SCE_IRQn`，不勾的话
     `ESR.TEC=128` 但软件 `err=0`——硬件在报错，软件看不见

最终：`rx id=0x123` 出现在 F407 的串口上，跨型号互通成立。

## 三、AI 的判断错误与纠正（重要）

这份记录如实保留 AI 的误判，因为**发现并纠正 AI 的错误本身就是能力**。

| # | AI 说过的错话 | 事实 | 怎么发现的 |
|---|---|---|---|
| 1 | "一块板 + 120 Ω 跨接 CANH/CANL 就能自己发自己收" | CAN 协议要求**另一个节点**给 ACK，单节点必然 ACK 错误 | 查协议 + 实测 `LEC=3` |
| 2 | "F407 的 APB1 也是 36 MHz，CAN 配方可以照抄" | F407 的 PCLK1 是 **42 MHz**（168/4） | 生成代码后核对 `PCLK1=42000000`，重算分频 |
| 3 | "rx=50 是模块把 TX 回环到 RX" | 是 B 板在正常发帧 | 改成按 ID 过滤一验即知 |
| 4 | 栈溢出钩子用带队列的日志 | 中断关闭上下文不能用 RTOS 队列 | 钩子没输出 → 改直写 UART |

**协作上的做法**：AI 给出结论后，人要求"给出可验证的现象"，
然后按现象实测。凡是实测和 AI 说法不符的，一律以实测为准，并回头改文档。

## 四、结论

- AI 在**代码实现、寄存器级排障、文档起草**上节省了大量时间
- 但**硬件现象、供电、接线、拔插验证**必须人来做，AI 无法替代
- 更重要的是：**AI 的结论必须用实测校验**。本项目四个明显误判都是靠实测抓出来的

如果只看"AI 生成代码"的部分，会觉得很快；真正花时间的是
**"怀疑—验证—修正"**这个循环，而这部分恰好是这个项目最有价值的地方。
