# 失败路径实测矩阵

> 日期：2026-11-20 · STM32F103C8T6 @72 MHz · 五任务 + 异步日志版本
> 目的：证明"不允许静默失败"这条要求不是写在文档里的口号，而是逐条测过的行为。

## 一、六条路径总表

| # | 故障 | 检测方式 | 上报内容 | 系统表现 | 恢复 |
|---|---|---|---|---|---|
| 1 | I2C 从机中途掉线 | `HAL_I2C_Mem_Read` 超时/错误 | `mpu lost, recovery...` | 业务继续，CAN 不受影响 | **自动**：DeInit → 9 个 SCL 时钟 → Init，4 ms |
| 2 | CAN 对端断电 | 发送邮箱满 | `can send failed: Timeout` | 任务不阻塞、不 while(1) | 对端上电后自动恢复 |
| 3 | CAN 总线不存在（收发器没电/断线） | `HAL_CAN_Start` 超时 | `can: start failed st=1 state=5 err=0x00020000 MSR=.. ESR=..` | 只降级 CAN，其余任务照跑 | 总线恢复后重启即好 |
| 4 | 传感器上电时就不存在 | `HAL_I2C_IsDeviceReady` 失败 | `probe failed (Busy)` → `mpu init -> Busy` | **故障隔离**：CAN 的 rx 照常 | 手动上电后恢复 |
| 5 | 日志队列灌满 | 队列 put 失败 | `logdrop` 计数增长 | **业务零影响** | 自动（消费者继续排空） |
| 6 | 任务栈溢出 | FreeRTOS `configCHECK_FOR_STACK_OVERFLOW=2` | `!!! STACK OVERFLOW in task [Comm] !!!` | 立即停住并点名 | 手动（修栈大小） |

## 二、逐条证据

### 路径 1：I2C 从机中途掉线

操作：运行时拔掉 SDA，3 秒后插回，不按复位。

```
[I][352930] acc[-1012,2752,18792] gyro[-149,-50,0]     ← 掉线前正常
[W][353985] mpu lost, recovery...                       ← 1 s 后检测到
[W][353988] i2c: bus recovery start
[W][353992] i2c: recover done, re-init Ok               ← 4 ms 完成恢复
[W][355047] mpu lost, recovery...                       ← 线没插稳，再恢复一次
[I][356060] acc[-1460,1928,19356] gyro[-218,-83,0]      ← 插回后自动继续
```

要点：错误被**检测到、上报、并自动恢复**，全程不需要人工复位。

### 路径 2：CAN 对端断电

操作：把 B 板断电，A 板继续发帧。

```
[W][47035] can send failed: Timeout
[W][47161] can send failed: Timeout
[I][47419] acc[-1216,108,18128] gyro[-139,-3,0]    ← 传感器任务照常
```

要点：三个发送邮箱被占满后，`send()` **按 timeout 返回错误码**，而不是死等。
对比参考框架的 `while(1)` 写法，这里系统仍然完全可用。

### 路径 3：CAN 总线不存在

操作：TJA1050 没有 5V（蓝药丸只靠 J-Link 3.3V 供电时 5V 引脚没电）。

```
[E][824] can: start failed st=1 state=5 err=0x00020000 MSR=0x00000409 ESR=0x00000000
[I][832] can start -> BusError
[I][1513] mpu6050: WHO_AM_I=0x68 ok        ← 其他外设正常
```

根因链（用寄存器定位）：

```
GPIOA->IDR bit11 = 0  → CAN_RX 被拉低（显性）
CAN->MSR INAK = 1     → 控制器出不了初始化模式（需要 11 个连续隐性位）
CAN->ESR = 0          → 一次位错误都没有，帧根本没发出去
模块 VCC 无 5V        → TJA1050 断电，RXD 输出低
```

**关键：错误信息里带了 `st / state / ErrorCode / MSR / ESR` 五个字段**，
否则只会看到一句 "start failed"，还要重新插调试器去查。

### 路径 4：传感器上电时就不存在

操作：拔掉 MPU6050 的 VCC（模块仍挂在 I2C 总线上），复位。

```
[E][342] mpu6050: probe failed (Busy)
[I][342] mpu init -> Busy
[W][344] mpu init failed, try bus recovery
[W][344] i2c: bus recovery start
[W][356] i2c: recover done, re-init Ok
[W][358] mpu read lost (NotInit), recovery...
[I][1069] rx id=0x456 len=8 seq=17184      ← CAN 完全不受影响
[I][2079] rx id=0x456 len=8 seq=17194
```

**一个意外发现**：错误码是 `Busy` 而不是预期的 `NoAck`。原因是
**MPU6050 模块上的 4.7k 上拉电阻和模块共用 VCC**，模块一断电，SCL/SDA 立刻失去上拉被拉低，
总线上根本发不出起始条件，所以 HAL 报"忙"而不是"无应答"。

这暴露了一个真实的设计缺陷：**I2C 上拉不能只依赖从机模块**。
改进方向：主机侧加 4.7k 上拉，或在连续 BUSY 后把引脚切成开漏并启用内部上拉再试。

### 路径 5：日志队列灌满

操作：临时开 `-DLOG_OVERFLOW_TEST`，每 5 秒灌 40 条日志（队列深度只有 12）。

```
[I][5015]  stats: tx=49 rx=49 drop=0 err=0 busoff=0 logsent=21 logdrop=0
[I][5015]  burst 0 ...（40 条突发）
[I][10016] stats: tx=99 rx=99 drop=0 err=0 busoff=0 logsent=47 logdrop=30
```

要点：
- 40 条突发里有 **30 条被丢弃**（队列装不下）
- **CAN 的 tx/rx 从 49 → 99 完全正常**，一帧不丢
- 丢弃被 `logdrop` 计数上报，不是静默丢掉

这就是异步日志的核心取舍：**宁可丢日志，也不让业务任务阻塞；但丢了多少必须算得出来。**

### 路径 6：任务栈溢出

操作：开 `configCHECK_FOR_STACK_OVERFLOW=2`，把 Comm 任务栈临时改成 200 字节
（正常 1024），编译 `-DSTACK_TEST_SMALL`。

```
[I][13] app layer ready (C++17, HAL-free)
[I][13] can: started (filter id=0x456, FIFO0 irq on)
[I][13] can start -> Ok (accept id=0x456)
!!! STACK OVERFLOW in task [Comm] !!!
```

对比"没开检查"时的表现：

| | 无检查 | 有检查 |
|---|---|---|
| 现象 | 跑几十秒后静默停住 | **13 ms 内点名任务** |
| 线索 | `CFSR=0x400 IMPRECISERR`，现场已丢失 | `STACK OVERFLOW in task [Comm]` |
| 定位 | 读寄存器 + 反查 PC，约 20 分钟 | 一眼 |

**踩的坑**：钩子第一版调用了带队列的日志函数 `common_log_info`，
但钩子运行在**中断关闭**的上下文，RTOS 队列不可用 → 钩子自己发不出消息，系统依旧静默停住。
改成直接写 USART 的 `common_log_sync()` 才成功。

> 教训：**"报错路径"本身也必须被测试**。日志系统再完善，如果崩溃时它不能用，等于没有。

## 三、设计上的四条规则（从上面六条总结）

1. **任何阻塞操作都要有超时**，超时后返回错误码，绝不 `while(1)` 死等
2. **错误信息要足够定位问题**：至少带错误码 + 外设状态寄存器，否则等于没报
3. **能自动恢复的必须自动恢复**（I2C 总线锁死、CAN bus-off），不能靠人按复位
4. **报错路径要能在最恶劣上下文里工作**（中断关闭、栈已坏、队列不可用）
