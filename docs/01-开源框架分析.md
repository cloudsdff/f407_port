# 读完 basic_framework 串口部分的一些想法

读的是 `bsp/usart/bsp_usart.h` 和 `bsp_usart.c`，加起来两百多行，一下午能读完。

整体感觉：这个框架能用，作者也很清楚自己在绕什么坑，但边界不太干净，有些地方的做法我不太认同。下面分开说。

## 写得好的地方

第一个是用枚举把发送方式收成一个参数。头文件里定义 `USART_TRANSFER_BLOCKING`、`USART_TRANSFER_IT`、`USART_TRANSFER_DMA` 三个值，`USARTSend` 里用一个 switch 分派到 HAL 的三个函数。

调用的人只需要说"我这一帧用 DMA 发"，完全不用管 DMA 怎么配、中断怎么开。任务一要求"外设只通过统一接口暴露"，这就是个现成的样板。

第二个是回调注册。模块把自己解析数据的函数交给 bsp，bsp 存起来，中断来了就调它。整个 bsp 层里搜不到"遥控器"或者"视觉"这种词，却能把这些数据送到对应模块去。

第三个是出错之后会自动重启接收。校验错、溢出、帧错这些，HAL 会调 `HAL_UART_ErrorCallback`，作者在里面重新开了一次 DMA 接收。这样偶尔错一次不会把整条串口废掉。

## 我觉得有问题的地方

### 一、`USARTIsReady()` 这里运算符写错了

`bsp_usart.c:85`：

```c
if (_instance->usart_handle->gState | HAL_UART_STATE_BUSY_TX)
    return 0;      // 忙
```

这里用的是按位或 `|`，不是按位与 `&`。

按位或的意思是：只要 `gState` 有任何一位是 1，或者右边那个常量本身非零，整个表达式就非零。所以不管串口是空闲还是在发送，`if` 都成立，函数永远返回 0，也就是永远说"忙"。

我算了一下，就算 `gState` 是 0，`0 | 0x20` 还是 `0x20`，照样非零。所以这个函数现在等于恒返回"未就绪"。

后果是任何"发之前先问一句能不能发"的模块，第一次问就被判忙，一帧都发不出去。

而且这解释了头文件第 55 到 59 行那个 `@todo`。作者在那里写"连续调用 IT/DMA 会让上一次发送被取消，要不要加个发送队列"。想做队列，就必须知道上一笔发完没有，而这函数永远说没发完，所以这个 todo 大概就卡在这里。

我会改成：

```c
if ((gState & HAL_UART_STATE_BUSY_TX) != 0) return 0;
return 1;
```

不过我的做法不只是改运算符。我会把接口设计成 `Err write_async(...)`，上一次没发完就返回 `Err::Busy`，让调用的人明确知道"这次没发出去"，而不是自己轮询一个布尔值。

### 二、出错就 while(1) 死循环，而且函数都返回 void

`bsp_usart.c` 里有三处这样写：第 42 行实例数超了、第 47 行重复注册、第 77 行发送模式非法，处理方式都是 `while (1)` 里打个日志，然后永远停在那儿。

另外第 49 行 `malloc` 之后没有检查返回值，紧接着就 `memset(instance, 0, ...)`。堆不够的时候 `malloc` 返回 NULL，`memset(NULL, ...)` 直接 HardFault。

这两个问题其实是同一件事的两面：整个文件的对外函数要么返回 `void`，要么返回一个不说明失败的指针。错误发生了，出不了这个函数，上层什么都收不到。

板子上表现就是"突然不动了"，你去看串口也没有新东西，只能靠猜。

我打算统一改成返回 `Err`。名册满了返回 `Overflow`，重复注册返回 `Busy`，参数不对返回 `InvalidParam`，分配失败也返回一个错误码，让调用的人自己决定是重试还是报警。总之不要在库里面替别人决定"卡死"。

### 三、中断里直接调用模块的解析函数

`bsp_usart.c:110` 这行 `usart_instance[i]->module_callback();` 是在中断服务程序里执行的。也就是说模块的协议解析代码实际上跑在串口中断的上下文里。

如果某个模块的解析函数里做了下面任何一件事，整个系统就挂：

调 `printf` 会死锁，因为打印要发串口，而发送完成的中断本身正被这个中断压着，等不到。

调 `HAL_Delay` 会卡死，因为它等的是 SysTick。

如果用了 FreeRTOS 的互斥锁，在中断里拿锁会被断言的。

同一个问题在第 135 行也有，`ErrorCallback` 里打了 `LOGWARNING`，也是中断上下文。

我的做法是中断里只投递，不解析。收到数据就 `osMessageQueuePutFromISR` 丢进队列，然后让任务去解析。任务优先级可以控制，可以被更高优先级打断，出问题也能用调试器看栈。

### 四、头文件里直接写了函数体

`bsp/bsp_init.h:16` 这一行：

```c
void BSPInit() { DWT_Init(168); BSPLogInit(); }
```

函数体写在头文件里，也不是 static 或者 inline。这个文件现在只被一个地方包含，所以没事。但只要将来有两个 .c 文件 include 它，链接的时候就会报重复定义。

而且这个文件开头还 `#include "bsp_init.h"`，是自己包含自己，靠头文件的 ifndef 才没出事。我觉得这属于"碰巧能用"，不算对。

## 我打算怎么做

结构上还是要学它：application、modules、bsp 三层，上层只能看见下层。这一点是对的，换芯片的时候能省很多事。

但接口我用 C++ 的纯虚类，不用结构体加函数指针。好处是该实现的函数不实现，编译就过不去，不会等到运行时才发现某个回调是空的。

错误码统一用 `Err`，所有对外函数都返回它，失败一律记日志加返回，不写 `while(1)`。断开设备、通信超时这种，要让上层能知道，能降级。

中断只投递队列，解析放任务里。

先把 `bsp_uart` 写出来验证这套想法，然后再往上写 module 层。
