# UART 实测记录（阻塞 vs DMA）

日期：2026-11-19 · 板子：STM32F103C8T6 @72 MHz · 波特率 115200 8N1

## 一、测试方法

在 `app/app_main.cpp` 里放了一个压测任务，按顺序做四件事：

1. 单帧发送：写 256 字节，然后等 `is_idle()` 为真
2. 越界保护：往 256 字节的缓冲里塞 300 字节，看返回什么
3. 忙保护：连续发两帧不等完成，看第二次返回什么
4. 连续发送 100 帧 × 256 字节（共 25600 字节）

数据模式：第 j 字节 = (seq + j) & 0xFF，每帧的 seq 递增 1。
PC 端把收到的原始字节按"帧内相邻字节差 1"检查，就能看出有没有错位、丢包。

## 二、实测结果

```
[I][1040] single frame: write=Ok idle=yes
[I][1044] overflow test (300B) -> Overflow
[I][1071] busy test: first=Ok second=Busy
[I][3375] bulk: ok=100 busy_retry=2277 err=0 idle_timeout=0 bytes=25600
[I][3382] === UART DMA test done ===
```

PC 端字节校验：

```
原始字节: 27081
完整 256 字节帧数量: 102
```

102 = 单帧 1 + 忙测试 1 + 批量 100，**一帧不多一帧不少，且每帧内部 256 个字节连续递增**。

## 三、几个能算出来的结论

**1. 吞吐接近理论极限**

100 帧共 25600 字节，从 1071 ms 到 3375 ms，用时约 2304 ms：

```
25600 B / 2.304 s ≈ 11113 B/s
115200 8N1 的理论上限 = 115200 / 10 = 11520 B/s
效率 ≈ 96.5%
```

也就是说 DMA 方式基本把 115200 的带宽用满了，中间几乎没有 CPU 参与的空档。

**2. busy_retry = 2277 说明了什么**

100 帧总共重试 2277 次，平均每帧 22.8 次。而 256 字节 @115200 的传输时间正好是：

```
256 × 10 bit / 115200 ≈ 22.2 ms
```

主循环用 `osDelay(1)` 重试，于是每次发送大约要等 22 ms 才能拿到下一个空位。
**这个数字反过来验证了"一帧 256 字节确实需要 22 ms"**，也说明 `Err::Busy` 的保护是必要的：
如果不做忙保护，这 2277 次调用会全部变成"覆盖上一帧，数据错乱"。

**3. 越界和忙都有明确返回值**

```
300 字节 → Err::Overflow（不截断发送）
连发两帧 → 第二次 Err::Busy（不覆盖）
```

对比参考框架：它的 `USARTIsReady()` 用按位或写错了，永远返回"忙"，
而 `USARTSend` 自己不做任何保护，连续调用 IT/DMA 会互相取消。

## 四、踩到的三个坑（按发现顺序）

### 坑 1：没配 DMA 就调 `HAL_UART_Transmit_DMA` → 直接 HardFault

CubeMX 里没给 USART1 开 DMA 时，`huart1.hdmatx` 是 NULL，
HAL 内部解引用空指针，整机停住、一个字都不输出。

加了守卫之后变成明确报错：

```cpp
if (kHuart->hdmatx == nullptr) return common::Err::NotInit;
```

现象从"静默崩溃"变成"每一帧都报 NotInit"，这就是"不许静默失败"的实际收益。

### 坑 2：只开 DMA 中断、没开 USART1 全局中断 → 串口永久停在 BUSY_TX

HAL 的 DMA 发送是两段式中断：

```
DMA 搬完最后一个字节
  └─ DMA1_Channel4 中断 → UART_DMATransmitCplt()
       └─ 打开 USART 的 TC（发送完成）中断
            └─ USART1 中断 → HAL_UART_TxCpltCallback() → 清忙标志
```

只开前者，`gState` 永远停在 BUSY_TX，于是：

- 我们的 `g_tx_busy` 永远不清，压测任务空转
- **所有 printf 都变成 `HAL_UART_Transmit` 立即返回 HAL_BUSY，字符被丢掉**
- 现象是"发出第一帧 256 字节之后就彻底安静"，看起来像死机，其实没崩

### 坑 3：DMA 发送过程中调用 printf

printf 也走同一个串口。DMA 正在发的时候打印，HAL 直接返回 HAL_BUSY，字符被丢弃，
日志行会缺字甚至整行消失（我第一次就是因此看不到 `single frame` 和 `bulk` 两行）。

规则：**打印前先确认 `is_idle()`**，或者干脆把日志攒起来等发完再打。
D13 做异步日志（队列 + 低优先级任务）就是为了根治这件事。

## 五、和参考框架的对比

| | 参考框架 `bsp_usart` | 本项目 `bsp::Uart` |
|---|---|---|
| 连续发送 | 头文件里写着 `@todo 是否考虑增加发送队列`，实际会互相取消 | 上一帧没发完返回 `Err::Busy`，调用方自己决定重试或放弃 |
| 越界 | 无检查，`uint16_t` 直接截断 | `len > 256` 返回 `Err::Overflow` |
| 发送方式选择 | 枚举 + switch | 纯虚接口分两个函数（`write` / `write_async`） |
| 失败处理 | `while(1)` 死循环 | 返回 `Err`，由上层决定 |
| 忙判断 | `gState \| BUSY_TX`（永远真） | `gState & BUSY_TX` 的判断在 HAL 内部，我们只维护自己的 `g_tx_busy` |
