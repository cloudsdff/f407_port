# CAN 双节点实测记录

日期：2026-11-20 · 两块 STM32F103C8T6 @72 MHz · CAN1（PA11/PA12）500 kbps
外设：TJA1050 收发模块 ×2（模块自带 120 Ω 终端，实测 122 Ω）

## 一、硬件连接

```
蓝药丸(A) ─ TJA1050#1 ─┬─ CANH ──── CANH ─┬─ TJA1050#2 ─ ATK板(B)
                        └─ CANL ──── CANL ─┘
         GND ──────────────────────────────── GND
   两模块各 120Ω → 整条总线实测约 60Ω
```

| TJA1050 | 接 MCU |
|---|---|
| VCC | **5V**（模块要 5V，3.3V 不够） |
| GND | GND |
| CTX | PA12（CAN_TX，丝印 A12） |
| CRX | PA11（CAN_RX，丝印 A11） |

## 二、位时序（500 kbps）

```
PCLK1 = 36 MHz
Prescaler = 4        → 9 MHz 时间基准
BS1 = 15 TQ
BS2 = 2 TQ
SJW = 1 TQ
每位 = 1 + 15 + 2 = 18 TQ
9 MHz ÷ 18 = 500 kbit/s
```

CubeMX 生成后已核对：`hcan.Init.Prescaler=4 / TimeSeg1=CAN_BS1_15TQ / TimeSeg2=CAN_BS2_2TQ`。

## 三、双节点互通结果

A 节点（蓝药丸，发 0x123、只收 0x456）串口输出：

```
[I][813] can: started (filter id=0x456, FIFO0 irq on)
[I][819] can start -> Ok (accept id=0x456)
[I][925] rx id=0x456 len=8 seq=3549
[I][1030] rx id=0x456 len=8 seq=3550
[I][1135] rx id=0x456 len=8 seq=3551
[I][1240] rx id=0x456 len=8 seq=3552
...
[I][5877] can stats: tx=49 rx=50 drop=0 err=0 busoff=0
```

几点说明：

- 帧间隔 **105 ms**：B 的任务 `osDelay(100)` + 一帧 8 字节传输（约 0.2 ms）+ 任务调度开销
- `seq` 从 3549 开始，说明 B 上电后已连续发送 3500+ 帧，中间没有断
- `drop=0`：接收队列（16 帧）没溢出，说明取帧速度跟得上 10 Hz
- `err=0 busoff=0`：总线上没有错误帧

## 四、过滤器：不是"能用就行"，是必须做对

第一版用的是**全通过滤器**（掩码全 0），结果是 A 把**总线上所有帧**都收进来，`rx` 计数里混着对方的和自己的。改成按 ID 过滤后：

```cpp
// 标准 ID 在 32 位过滤器里位于 bit31..21
const uint32_t stid = (accept_std_id & 0x7FF) << 21;
filter.FilterIdHigh   = (stid >> 16) & 0xFFFF;
filter.FilterIdLow    = stid & 0xFFFF;
filter.FilterMaskIdHigh = ((0x7FF << 21) >> 16) & 0xFFFF;  // 只比较这 11 位
filter.FilterMaskIdLow  = (0x7FF << 21) & 0xFFFF;
```

A 只放行 `0x456`、B 只放行 `0x123`，各自发出去的帧被**硬件丢弃**，`rx` 计数才干净。

## 五、踩到的坑（按排查顺序）

### 坑 1：模块没有 5V → HAL_CAN_Start 超时

现象：`can: start failed`，`state=5`（HAL_CAN_STATE_ERROR），`ErrorCode=0x00020000`（TIMEOUT）。

排查过程：

| 步骤 | 手段 | 结果 |
|---|---|---|
| ① 看状态寄存器 | 读 `CAN_MSR` = 0x409 | `INAK=1` → 控制器卡在初始化模式 |
| ② 看错误寄存器 | 读 `CAN_ESR` = 0 | 一次位错误都没有，说明帧根本没发出去 |
| ③ 看引脚电平 | 读 `GPIOA->IDR` 的 bit11 | **PA11 = 0（显性）** |
| ④ 查供电 | 万用表量模块 VCC | 模块没有 5V |

根因：蓝药丸靠 J-Link 的 3.3V 供电时，**板上 5V 引脚是没电的**（没有升压电路），TJA1050 断电后 `RXD` 输出被拉低 → PA11=0 → 控制器认为总线显性 → 等不到 11 个隐性位 → 永远出不了初始化模式。

解决：给蓝药丸插自己的 USB（5V 引脚有电），J-Link 只做调试器。

**这条要记住：CAN 控制器退出初始化需要总线上连续 11 个隐性位，收发器没电就等于总线被拉死。**

### 坑 2：bus-off 恢复没有退避，会把总线霸占

B 板单独上电时没有节点给它 ACK，发送错误计数 TEC 涨到 255 → Bus-Off；固件里的恢复逻辑立刻重启 → 又发 → 又 bus-off，循环往复，总线被持续占用，导致后上电的 A 板无法完成初始化。

对策（待实现）：恢复前加退避延时（例如 1 s），并统计连续失败次数，超过阈值就只收不发。

### 坑 3：全通过滤器让统计失去意义

见第四节。真实总线上多节点时，必须用过滤器把"自己的"和"别人的"分开。

## 六、和参考框架的对比

| | 参考框架 `bsp_can` | 本项目 `bsp::Can` |
|---|---|---|
| 接收 | 中断里直接解析 | 中断只搬进环形队列，解析交给任务 |
| 发送失败 | 不检查 | 邮箱满时按 timeout 等待，返回 `Err::Timeout` |
| 错误处理 | 打日志 | 四个错误中断全开 + bus-off 自动恢复 + 计数上报 |
| 过滤器 | 固定配置 | 按对端 ID 动态配置 |
| 诊断 | 无 | `tx/rx/drop/err/busoff` 五个计数器 |

## 七、为什么 CAN 没有 DMA

bxCAN 的发送机制本身是"3 级邮箱"：把报文写进邮箱寄存���，硬件自己仲裁、发送、重传，**CPU 不参与搬运**，因此不存在"DMA 搬运 CAN 数据"这个机制。

接收侧同理：报文进 FIFO，靠 FIFO 挂起中断通知 CPU。
所以 CAN 的"两种方式"是**阻塞发送 + 中断接收**，而不是"阻塞 + DMA"。这一点在任务01 的文档里要主动说明——比硬凑三种方式更像懂行。
