# 任务设计（FreeRTOS）

> 首次实测：2026-11-16（双任务）· 任务划分定稿：2026-11-20（五任务）
> 板子：STM32F103C8T6 @72 MHz · FreeRTOS 10.x（CMSIS-RTOS2 封装）

## 一、任务表（全部为实测值）

| 任务 | 优先级 | 周期 | 栈分配 | 实测剩余栈 | 通信方式 | 职责 |
|---|---|---|---|---|---|---|
| `task_led` | Normal | 200 ms | 2048 B | — | — | LED 心跳（CubeMX 生成） |
| **`Comm`** | **AboveNormal** | **1 ms** | **1024 B** | **352 B** | CAN 环形队列（16 帧） | CAN 收发、bus-off 恢复、统计 |
| **`Sensor`** | Normal | **5 ms** | **1024 B** | **360 B** | I2C 直读（阻塞约 1.3 ms） | MPU6050 采样 |
| `task_log` | Low | 500 ms | 2048 B | 1296 B | 日志队列 | 栈水线观察（CubeMX 生成） |
| **`log_task`** | **BelowNormal1** | 事件驱动 | 512 B | — | 消息队列（12 × 80 B） | 异步日志发送 |

### 为什么这样划分

**Comm 优先级最高（AboveNormal）**：CAN 是唯一的实时通信链路，1 ms 周期必须保证。
它的工作时长很短（收一帧 + 每 100 ms 发一帧），不会长时间占 CPU。

**Sensor 次之（Normal）**：MPU6050 通过 I2C 阻塞读一次约 1.3 ms（14 字节 @100 kHz），
5 ms 周期下占约 26% 时间片。放在 Comm 之下，保证 CAN 不被 I2C 阻塞拖慢。

**log_task 最低（BelowNormal1）**：日志是"尽力而为"的服务，任何业务任务都能抢占它——
这正是"打印不能阻塞业务"的实现方式。

**`task_led` / `task_log` 保持 CubeMX 生成的 2048 B**：它们跑的是生成的原始任务体，
栈需求低，但没改动生成代码，保留原配置方便对比。

## 二、系统配置

| 项 | 值 | 说明 |
|---|---|---|
| `configTICK_RATE_HZ` | 1000 | 1 tick = 1 ms |
| `configMAX_PRIORITIES` | 56 | CMSIS-RTOS2 默认 |
| **`configTOTAL_HEAP_SIZE`** | **10240** | 五任务栈合计 6656 B + TCB + 日志队列 960 B |
| HAL 计时源 | **TIM4**（1 kHz） | SysTick 让给 FreeRTOS |
| 调度方式 | 抢占式 + 时间片 | — |

> ⚠️ CubeMX 每次 GENERATE 都会把 `TOTAL_HEAP_SIZE` 重置为 3072。
> 正确做法：在 `FREERTOS → Config parameters` 里设成 10240 再生成，否则要手动改 `FreeRTOSConfig.h`。

## 三、异步日志

### 结构

```
业务任务 → snprintf 到栈上 80 B 缓冲 → 入队（永不阻塞）
                                        ↓
                        log_task（BelowNormal1）→ 逐字节发 USART1
```

### 为什么要异步

实测一行 33 字节 @115200 需要 **2.9 ms**（见 docs/02-UART实测记录.md）。
若让 1 ms 周期的 `Comm` 任务直接 printf，周期会变成 3.9 ms——实时性直接崩。
改成异步后业务任务只花约 0.1 ms 做格式化 + 入队。

### 参数依据

| 参数 | 值 | 依据 |
|---|---|---|
| 队列深度 | 12 | 生产者约 4 条/秒，消费者约 300 条/秒，深度 12 足以吸收突发 |
| 槽位大小 | 80 B | 最长的一条日志（stats 行）约 70 字符 |
| 满载策略 | 丢弃 + 计数 `logdrop` | **绝不阻塞业务任务** |

### 验收数据

```
[I][5016]  stats: tx=49 rx=49 drop=0 err=0 busoff=0 logsent=21 logdrop=0
[I][10017] stats: tx=99 rx=99 drop=0 err=0 busoff=0 logsent=37 logdrop=0
[I][15018] stats: tx=148 rx=148 drop=0 err=0 busoff=0 logsent=53 logdrop=0
[I][15018] stack free: Comm=352 Sensor=360
```

`logsent` 每 5 秒增长约 16 条（与生产速率一致），`logdrop=0` 说明吞吐匹配。

## 四、踩过的坑

### 坑 1：栈溢出表现为"不精确总线错误"

现象：跑几十秒后整机停住，串口再无输出。

诊断（J-Link 读内核寄存器）：

```
CFSR = 0x00000400   IMPRECISERR（写坏了某个地址，但现场已经过去）
HFSR = 0x40000000   FORCED（升级为 HardFault）
PC   落在 prvIdleTask 附近
```

根因：新版日志函数在栈上开 `body[96]` + `line[96]`，加 `vsnprintf` 内部约 150 B，
一次调用吃约 350 B 栈；而 `Comm` 任务栈只有 512 B。

修法：
1. 日志改单缓冲（前缀与正文写在同一块），省 96 B
2. `Comm` / `Sensor` 栈提到 1024 B
3. 堆 8192 → 10240

**教训：栈溢出不会在你写错的那一行报错，可能十几秒后以完全不相关的方式崩。**

### 坑 2：日志队列溢出

第一版深度 8、槽位 96 B，跑 20 秒 `logdrop=29`（约 1/3 日志被丢）。
调整：深度 8→12、槽位 96→80、Log 任务优先级 `osPriorityLow`→`osPriorityBelowNormal1`，之后 `logdrop=0`。

**异步化不是"加个队列"就完事，深度 / 槽位 / 消费者优先级要一起算。**

### 坑 3：两个 `task_log` 重名

CubeMX 生成的 `StartTaskLog` 每 500 ms 打一条，与我们自己的 `log_task` 名字冲突。
处理：生成的任务保留（当作心跳 + 栈水线观察），所有日志统一走 `common::log_impl`。

## 五、资源占用

```
RAM:   16640 B / 20480 B  (81.25%)
FLASH: 54148 B / 65536 B  (82.62%)
```

- RAM：10240 B 是 FreeRTOS 堆，其余是 HAL 句柄、缓冲、队列
- **Flash 已到 82.6%**，后续加模块前先把构建类型从 `Debug` 换成 `-Os`（约省 20–30%）

## 六、待改进

- `Sensor` 的 5 ms 周期里 I2C 阻塞占 1.3 ms（26%），后续可改中断/DMA 读取释放 CPU
- `stack_free` 目前只覆盖 Comm/Sensor，`task_led` 和 `log_task` 的水线没测
- 日志丢弃策略是"丢最新的"，可考虑"丢最旧的"以保留最近现场
