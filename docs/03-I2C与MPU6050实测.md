# I2C 与 MPU6050 实测记录

日期：2026-11-19 · 板子：STM32F103C8T6 @72 MHz · I2C1 标准模式 100 kHz

## 一、硬件与接线

| MPU6050 | 蓝药丸 | 说明 |
|---|---|---|
| VCC | 3.3V | 模块板载 4.7k 上拉 |
| GND | GND | — |
| SCL | PB6 | I2C1_SCL |
| SDA | PB7 | I2C1_SDA |
| AD0 | GND | 地址 = 0x68（接 3.3V 则是 0x69） |
| INT | 不接 | 本项目用轮询/中断读，不用数据就绪中断 |

## 二、初始化与读取结果

```
[I][1515] mpu6050: WHO_AM_I=0x68 ok
[I][1520] mpu6050: init done (accel +-2g, gyro +-2000dps)
[I][1525] mpu init -> Ok
[I][1529] acc[532,736,18308] gyro[54,277,-1]
[I][2035] acc[512,772,18400] gyro[-138,0,0]
[I][2541] acc[564,676,18252] gyro[-139,-3,0]
```

- `WHO_AM_I = 0x68`：地址、上拉、接线全部正确
- 陀螺仪静止时接近 0（±150 LSB 抖动）：传感器确实在测量，不是输出垃圾
- 加速度 Z 轴约 18300 LSB

## 三、一个必须记下来的偏差：静止模长 1.119 g

```
sqrt(532² + 736² + 18308²) = 18331 LSB
18331 / 16384 = 1.119 g      （±2g 量程下 1g = 16384 LSB）
```

理想静止时模长应该等于 1.000 g，实测偏了 **+12%**。

这不是代码问题，是廉价 MPU6050 的常态：零偏（offset）和标度误差都存在。
影响与对策：

| 影响 | 对策 |
|---|---|
| 姿态解算时角度会有系统偏差 | 上电做零偏校准：静止采 N 帧求平均，之后每次减掉 |
| 模长不等于 1g，说明标度也可能偏 | 若要求高，需要做六面校准或查标度系数 |
| 任务02 明确要求"上电自校准与零漂抑制" | 这组数据就是那条要求的动机 |

**这组数据要留进文档**——它证明"读到了数据"和"数据可用"是两件事。

## 四、拔线自愈（关键验证）

操作：运行时把 SDA 线拔掉，3 秒后插回，全程不按复位键。

实测日志：

```
[I][352930] acc[-1012,2752,18792] gyro[-149,-50,0]      ← 拔线前正常读
[W][353985] mpu lost, recovery...                        ← 1 秒后检测到丢失
[W][353988] i2c: bus recovery start                      ← 进入恢复流程
[W][353992] i2c: recover done, re-init Ok                ← 4 ms 内完成重初始化
[W][355047] mpu lost, recovery...                        ← 线还没插稳，再恢复一次
[W][355050] i2c: bus recovery start
[W][355054] i2c: recover done, re-init Ok
[I][356060] acc[-1460,1928,19356] gyro[-218,-83,0]       ← 插回后数据自动恢复
```

三个要点：

1. **失败被检测到并上报了**（`mpu lost`），不是静默返回错误数据
2. **恢复动作自动执行**，4 ms 内完成 DeInit → 打 9 个时钟 → 重新 Init
3. **不需要人工复位**，插回后业务自己继续跑

对比参考框架的 `HAL_UART_ErrorCallback`：它出错后只是重启接收 + 打一条日志，
错误信息出不了那个函数（返回 `void`），上层无法知道刚才丢过数据。

## 五、F103 的 I2C1 errata 与恢复原理

现象：从机在传输中途被拔线时，会把 SDA 一直拉低；HAL 从此认为总线忙，
所有后续调用立刻返回 BUSY 或超时，**即使把线插回去也不会自己恢复**。

原因：I2C 协议里从机在等第 9 个时钟（ACK 位）把数据吐完，主机不再发时钟，
从机就一直攥着 SDA 不放。

恢复办法（`recover_bus()` 里实现）：

```
1. HAL_I2C_DeInit()            放弃当前控制器状态
2. 把 SCL(PB6) 临时配成推挽输出
3. 循环 9 次：SCL 高 → 延时 → SCL 低 → 延时
   （给从机 9 个时钟，让它把没发完的字节发完、释放 SDA）
4. HAL_I2C_Init()              重新初始化控制器
```

## 六、踩到的坑

| # | 坑 | 现象 | 处理 |
|---|---|---|---|
| 1 | 没开 I2C1 event 中断 | 异步读发起后永远 busy | CubeMX 里使能 `I2C1 event interrupt` |
| 2 | CubeMX 每次生成都会重置 `configTOTAL_HEAP_SIZE` 为 3072 | 任务创建失败、系统看似正常但没任务跑 | 每次生成后在 FreeRTOS 配置里改回 8192 |
| 3 | 不写 `PWR_MGMT_1 = 0x00` | 六轴数据全是 0 | 初始化里必须先唤醒，再做任何读取 |

## 七、接口设计（贴出来备查）

```cpp
// bsp 层
virtual Err write_reg(dev, reg, data, len, timeout);
virtual Err read_reg(dev, reg, data, len, timeout);       // 阻塞
virtual Err read_reg_async(dev, reg, data, len);          // 中断
virtual Err probe(dev, timeout);                          // 设备在不在
virtual Err recover_bus();                                // 总线锁死恢复

// module 层
Err init();                    // 探测 + 校验 WHO_AM_I + 唤醒 + 设量程
Err read_raw(Raw& out);        // 阻塞读 14 字节
Err read_raw_async(Raw& out);  // 中断读
```

module 层里没有任何 `HAL_`：数据怎么搬是 bsp 的事，模块只关心寄存器语义。
